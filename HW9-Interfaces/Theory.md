# ДЗ9. Интерфейсы и инверсия зависимостей

## 1.1. Контракт интерфейса

### 1. Почему `ProcessDamage` принимает `List<IDamageable>`?

`GameSystem` достаточно знать, что цель умеет получать урон через `TakeDamage`. Один список `List<IDamageable>` может содержать и `Player`, и `Trap`. При вызове метода через интерфейс выполняется реализация фактического объекта, поэтому игрок теряет здоровье, а ловушка разбивается. Новый тип цели можно добавить в тот же список, реализовав `IDamageable`, без изменения `ProcessDamage`. Готовый `List<Player>` напрямую передать нельзя, поскольку `List<T>` инвариантен.

### 2. Соблюдает ли `Trap` контракт?

С точки зрения компилятора `Trap` выполняет контракт, поскольку у него есть оба аксессора `HP` и метод `TakeDamage` с нужной сигнатурой. Если по смыслу `false` означает, что объект после удара разрушен, результат первого удара по одноразовой ловушке понятен. Ловушка продолжает показывать `HP == 10`, игнорирует запись в `HP` и сообщит о разрушении при повторном ударе. Если вызывающий код полагается на согласованность `HP` и результата удара или ожидает, что запись изменит здоровье, поведение ловушки нарушает эти ожидания. В текущем `ProcessDamage` это расхождение не заметно, потому что метод только вызывает `TakeDamage`.

### 3. Что будет, если передать зелье в `ProcessDamage`?

`HealthPotion` реализует только `IHealable`, поэтому его нельзя добавить в `List<IDamageable>`. Компилятор отклонит такую попытку или прямую передачу `List<IHealable>` в `ProcessDamage`. Если сначала скрыть тип зелья за `object`, а затем привести его к `IDamageable`, во время выполнения возникнет `InvalidCastException`. Даже у объекта, реализующего оба интерфейса, `ProcessDamage` вызовет `TakeDamage`, поскольку именно этот метод написан в его теле. Для вызова `Heal` системе нужен отдельный путь через `IHealable`.

### 4. Что изменится после добавления `IsDead`?

Свойство `bool IsDead { get; }` без реализации станет обязательной частью `IDamageable`. Его нужно реализовать в `Player` и `Trap`, поскольку оба класса реализуют этот интерфейс. Игрок может вычислять свойство как `HP <= 0`, а ловушка может хранить признак разрушения и обновлять его после первого удара. Если оставить классы как есть, компилятор сообщит, что они не реализуют член интерфейса. `HealthPotion` и методы `GameSystem` менять не требуется.

## 1.2. Абстрактный класс и интерфейс

| Утверждение | Abstract class | Interface | Комментарий |
| --- | :---: | :---: | --- |
| Может содержать поля с конкретными значениями | + | + статические, − экземпляра | Абстрактный класс может хранить состояние каждого экземпляра. Интерфейс допускает статические поля с инициализатором. |
| Может иметь полноценный конструктор | + | − для экземпляра | Конструктор абстрактного класса вызывается при создании объекта производного класса. У интерфейса возможен статический конструктор для инициализации самого типа. |
| Один класс может наследовать или реализовывать несколько таких типов | − | + | У класса может быть только один непосредственный базовый класс. Реализовать можно несколько интерфейсов одновременно. |
| Может содержать реализацию метода по умолчанию | + | + | Базовый класс может предоставить готовый метод, в том числе `virtual` для переопределения. Начиная с C# 8.0, интерфейс также может содержать реализацию метода по умолчанию. |
| Может объявлять свойства без реализации | + | + | Абстрактный класс объявляет такое свойство с модификатором `abstract`. Интерфейс может объявить требуемые аксессоры без тела. |
| Может быть использован как тип поля или переменной | + | + | Такая переменная или поле может ссылаться на экземпляр производного класса либо объекта, реализующего интерфейс. |
| Может наследовать классы | + | − | Абстрактный класс может иметь базовый класс. Интерфейс может наследовать другие интерфейсы. |
| Может содержать приватные методы | + | + | Класс может использовать приватные вспомогательные методы. Начиная с C# 8.0, интерфейс тоже может объявлять приватные методы с телом для своей внутренней логики. |

Сведения о современных интерфейсах сверены с документацией. [Справочник C#](https://learn.microsoft.com/dotnet/csharp/language-reference/keywords/interface)

### Типы игровых сущностей

```text
GameEntity (абстрактный класс, реализует IDamageable)
├── Player : GameEntity, IInteractable, IHealable
├── Enemy  : GameEntity
└── NPC    : GameEntity, IInteractable
```

`GameEntity` хранит общее состояние (`Name`, `HP`) и реализует правила получения урона. Абстрактный класс здесь выражает отношение «является игровой сущностью» и позволяет один раз написать общую логику инициализации и изменения здоровья. `IDamageable` даёт боевой системе отдельный контракт для работы с любыми целями, включая объекты без общего базового класса.

`IInteractable` объявляет открытие диалога, поэтому его реализуют `Player` и `NPC`. `IHealable` объявляет восстановление здоровья, и его реализует только `Player`. Интерфейсы позволяют одному классу поддерживать несколько независимых возможностей. Код диалога или лечения зависит только от нужного ему контракта.
